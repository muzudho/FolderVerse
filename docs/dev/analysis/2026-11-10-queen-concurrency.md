## 診断の方法

検証ソース：tests/QueenConcurrencyProbe/。
モデルのRobotCampaign.csは製品から２行だけ追加し、全戦闘の構築後・RunSegment開始前の読取コールバックを設けた。戦闘ルール・乱数・部隊・進行予算は変更しない。テストはそのコールバックで未完了盤のQueen ID重複を検出する。製品のコードは変更していない。

git diff v0.7.0 -- FolderVerse/RobotCampaign.cs は差分なし。この共通処理は公開v0.7.0と同じ。人間が確定した注文も同じRobotCampaign.Advanceに入るため、CPU固有の判断ミスとして扱わない。

## 原因候補・修正案

CreateEncounterは現在地点にいる防衛クイーンを補う際、既に他盤に出ているクイーンを確認するが、同ターン中にこれから構築する明示出撃を先取りしていない。防衛盤が先に構築されるとその後の出撃盤にも同じクイーンが入る。

当該ターンの有効なQueen出撃を先に確定し、そのクイーンを出発地の自動防衛へ追加しない方針が考えられる。出撃が取り消された場合の防衛復帰、予約到着の失敗、手動注文、継戦・分割盤・辺戦・捕獲後の帰還も含めた検証が必要。単に攻撃を禁止するCPU変更やクイーンを増やすルール変更で隠さない。利用者へ報告し、共通処理の修正として別途扱う。
